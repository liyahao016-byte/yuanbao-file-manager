# 元宝智能文件管理器 —— 基于内容的 AI 命名技术实现白皮书

## 1. 核心解答：当前技术能否实现？
**答案是：完全可以，且在当前架构中已经深度实现。**

元宝智能文件管理器并未停留在“根据旧文件名修修补补”的浅层能力，而是已经构建了一套**【深度内容解析 + 多模态 OCR + 本地大模型抽取】**的全栈技术链路，真正实现了“让 AI 看过文件正文后再起名”。

---

## 2. 技术架构与实现链路

为了让 AI 能够“阅读”文件内容，系统在底层构建了一条从物理文件到语义特征的解析流水线。

### 2.1 深度文本提取引擎 (`file_parser.rs`)
在进行 AI 命名之前，系统会首先通过 Rust 层的高性能解析器，强制读取文件内部的真实内容：
- **纯文本与代码文件 (TXT/MD/RS 等)**：直接读取原生的 UTF-8 文本内容。
- **Office 文档 (DOCX)**：底层解压 ZIP 容器，并解析 `word/document.xml` 节点，过滤出所有文字流。
- **矢量 PDF (Text PDF)**：使用 `pdf_extract` 库逐页提取原生内嵌的矢量文本层数据。

### 2.2 视觉与扫描件的破局：原生 OCR 降级链路
在现实办公中，大量文件是“扫描版合同PDF”或是微信接收的“发票截图”。针对这类**没有文本层**的文件，系统集成了 Apple macOS 底层的视觉引擎：
- **触发机制**：当 PDF 提取出的文字过少（<50 字符），或者遇到 `png/jpg/webp` 等纯图像格式时，Rust 底层会自动触发系统级的 C FFI 接口 (`macos_ocr_pdf_or_image`)。
- **执行过程**：调用苹果原生的 Vision Framework 进行硬件加速的 OCR 光学字符识别。
- **结果回流**：将识别出的合同条款、发票明细、发文红头等文字，无缝拼接到大模型的上下文（Context）中。

### 2.3 2000 字符的“黄金摘要”截取
考虑到本地大模型（如 `qwen2.5`）的上下文窗口限制以及推理性能，系统在完成解析后，会精准截取文件前 **2000 个字符**（`read_text_snippet(&path, 2000)`）。
- **科学依据**：绝大多数文档的核心要素（公文红头、合同甲乙方、报告标题与时间、发票抬头）均集中在文件的前两页。2000 字符足以覆盖这些高维元数据，兼顾了生成质量与推理速度。

### 2.4 大模型语义抽取与组装
将截取出的 2000 字内容摘要喂入 Ollama 本地模型，配合强大的 Prompt 指令引擎：
> *“你是一个专业的文件整理专家。请根据已知的内容摘要... 提取最核心的要素（如：核心主题、公司/人名、项目名、日期），用连字符拼接...”*

模型通过阅读这 2000 字，自主理解这是一份“中微公司2026年二季度的采购合同”，从而抛弃原本的乱码名 `wx_camera_1234.jpg`，输出极具业务价值的命名。

## 3. 现阶段的能力边界与未来演进

尽管当前基于前 2000 字符的局部内容抽取已经能解决 90% 的命名痛点，但从更极致的产品视角看，技术仍存在演进空间：

### 3.1 当前局限性
1. **摘要截断问题**：如果一份几百页的 PDF，其核心摘要、时间落款恰好在文档的最后一页（例如合同盖章页的生效时间），由于“前 2000 字符”的硬性截断，AI 将无法获取到真正的生效日期，从而只能生成缺省日期的名称。
2. **多模态图表理解**：如果一页 PPT 主要是复杂的财务柱状图，虽然有少量文字，但系统缺乏多模态视觉模型（VLM）的支持，无法真正理解图表代表的营收趋势。

### 3.2 演进方向 (Next Steps)
1. **引入轻量化 RAG（检索增强生成）**：针对超大文档，先在端侧对其全文进行分块 Embedding，然后将命名的 Prompt 转化为一次检索：`"这篇文档的核心主题是什么？时间落款是哪天？"`，从而突破 2000 字的物理限制。
2. **长尾特征动态捕获**：提取文档的前 1000 字符和**尾部 1000 字符**进行拼接组合，以保证“前言（标题）”与“后语（落款签名）”都能被 AI 同时阅览。
