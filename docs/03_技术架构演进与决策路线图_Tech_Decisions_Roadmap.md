## [2026-07-27] 动态工作场景/项目聚类与 Finder 定位及导出架构演进 (PRD 4.0)

### 决策背景
用户需要在具体工作/学习场景（如“期末复习资料”）或特定工程路径（如“元宝文件管理器项目”）下自动动态聚合文件，并具备灵活的现场 AI 动态建簇、簇卡片解散/自如沉浮，以及在任意文件列表中实现原生 Finder 高亮定位与物理导出的能力。

### 决策内容
1. **AI 动态建簇与后端响应引擎**：实现 Rust `create_custom_ai_cluster` 指令，支持用户在智能文件夹页面顶栏输入自然语言/关键词实时生成具象化场景卡片。
2. **双层绝对排序机制**：卡片排序应用 `📌 钉住顺序优先`（置顶） + `🖱️ 点击频次高者靠前/自然淡出`（后置沉浮）算法。
3. **原生 Finder 定位与文件导出**：实现 Rust `reveal_in_finder`（调用 `open -R <path>`）与 `export_files`（物理复制到指定路径），全量文件列表行悬浮提供对应一键操作按钮。
4. **归档文档**：全套方案已归档至 [06_日常办公高价值场景智能分类说明文档_Daily_Office_Smart_Folder_PRD.md](file:///Users/superli/Desktop/aiwork/文件管理器demo/docs/06_日常办公高价值场景智能分类说明文档_Daily_Office_Smart_Folder_PRD.md)。

## [2026-07-26] 智能文件夹算法与全景卡片技术架构演进

### 决策背景
原智能文件夹聚类仅依赖简单的字符串 N-Gram 匹配，当工作区存在海量屏幕截图时，聚类结果被单一类型的“企业微信截图”严重挤占，缺乏多元格式展示与用户可自定义交互。

### 决策内容
1. **多维混合聚聚类算法**：重构 `get_smart_folder_stats`，引入 4 大固定格式大类簇（图片、文档、表格、媒体）+ 智能过滤干扰词的 AI 语义主题簇。
2. **AI 主题拟名引擎**：在 `ollama.rs` 中新增 `generate_group_folder_name`，结合大模型多文件摘要实现聚合智能命名与降级保护。
3. **可拖拽卡片与综合双重下钻架构**：引入 `SmartFolderCard` 组件，支持拖拽排序、📌钉住、🗑️删除隐藏状态持久化，以及“就地快速预览”与“全视图完整下钻”双重交互。

## [2026-07-25] 收纳区独立化：Tauri 多窗口架构 (Desktop Dropzone Widget)

### 决策背景
原收纳区组件渲染于主渲染进程 Window (`App.jsx`) 内部，存在以下硬伤：
1. **遮挡主界面**：即使采用隐藏/滑动式 Drawer，依然会在拖拽时占用主程序可视面积，干扰文件管理器的日常浏览。
2. **定位与坐标解耦难题**：当主应用窗口移动、缩放或全屏时，内置 DOM 元素的绝对坐标频繁变动，影响原生 DragDrop 判定。

### 决策内容
将收纳区完全抽离为主应用外壳的 **独立桌面悬浮窗口 (QQ 闪传模式)**：
1. **Tauri 多窗口配置**：在 `tauri.conf.json` 配置 `dropzone` 独立窗口 (`url: "index.html?window=dropzone"`, `alwaysOnTop: true`, `transparent: true`, `decorations: false`)。
2. **跨进程事件总线**：借助 `@tauri-apps/api/event` 的 `emit`/`listen` 机制，在主窗口与收纳区窗口间实现 `refresh_workspace` 实时联动。
3. **真实文件操作统一**：收纳盒维持 `~/.yuanbao_staging` 的底层物理转移逻辑，支持文件拖入收纳与拖出导出。

## [2026-07-24] 收纳区架构回退：从“前端虚拟映射”切换为“物理文件迁移”

### 决策背景
在尝试使用“方案二（纯前端虚拟映射）”实现收纳区（Dropzone）拖放逻辑时，遇到了不可逾越的操作系统与框架底层限制：
1. **WebKit 原生安全限制**：Mac 的 Safari 内核在处理跨应用（或内部跨 WebView）拖放时，强制拦截并剥离自定义的 `dataTransfer` payload，导致前端无法稳定追踪被拖拽对象。
2. **React 合成事件代理冲突**：Tauri 的 `dragover` / `drop` 原生事件与 React 17/18 的合成事件在 DOM 冒泡路径上存在冲突，引发收纳区频繁接收失败并自动缩回。
3. **外部文件无缝拖入需求**：用户需要在系统的任意深层文件夹（Finder）中将实体文件拖入收纳区，虚拟映射无法完美覆盖物理层拖拽。

### 决策内容
全面废弃前端虚拟映射逻辑，采用“方案一”物理存储架构：
1. **统一的真实存放点**：在用户根目录下隐式创建 `~/.yuanbao_staging` 作为统一收纳目录。
2. **真实的文件位移**：Rust 端实现 `move_files_to_staging`，当拖拽完成时，真实执行 `fs::rename` 或 `fs::copy` 将文件移出原文件夹。
3. **完全信任物理层数据**：收纳区渲染数据不再通过前端过滤，而是直接拉取 `get_staging_files`，保证所见即所得。

### 优缺点评估
- **优势**：绝对稳定，不受限于浏览器内存栈，支持跨设备、跨应用的原生文件拖放。状态刷新通过 `refresh_workspace` 自动处理，逻辑极简。
- **代价/风险**：跨盘拖动时会有文件 IO 开销。原路径记录机制（为后续解散做准备）需要额外引入 SQLite 表进行跟踪，增加了一定的后端逻辑复杂度。

## 阶段一：底层架构与数据流构建
- **核心诉求**：突破纯 Web 前端限制，具备原生操作系统的文件扫描、本地数据库存储能力。
- **决策点 1：桌面外壳选型**
  - **选项**：Electron (Node.js) vs Tauri (Rust)
  - **最终选择**：**Tauri (Rust)**
  - **理由**：追求极致性能，要求极低的内存占用和极小的打包体积，这对于一个常驻后台、需要扫描海量本地文件的应用至关重要。
- **决策点 2：本地数据存储与纯文本检索**
  - **最终选择**：**SQLite (集成 FTS5 倒排索引)**
  - **理由**：SQLite 零配置、极轻量且成熟。开启 FTS5 虚拟表扩展后，可原生实现极速纯关键词全文检索。

## 阶段二：AI 模型管线与向量搜索
- **核心诉求**：脱离重度 Python 依赖，在端侧（Rust 层）实现向量 Embedding 与聚类算法。
- **决策点 1：AI 推理引擎架构**
  - **选项**：ONNX Runtime (内置模型) vs Ollama (外部服务进程)
  - **最终选择**：**Ollama (外部服务进程)**
  - **理由**：由于用户环境已安装 Ollama 及 Qwen 2.5 13B/32B，通过 HTTP (`http://localhost:11434`) 调度本地 Ollama 服务可以极大降低 Rust 客户端的安装包体积和构建复杂度。
- **决策点 2：模型分发与存储策略**
  - **最终选择**：**外部依赖 (Ollama Pull)**
  - **理由**：对于重命名等生成任务，使用用户现有的 `qwen2.5:32b`；对于向量检索任务，使用 `bge-m3` 模型。
- **决策点 3：向量数据库**
  - **最终选择**：**sqlite-vec**
  - **理由**：作为 SQLite 的轻量 C 语言插件，能与现存的 metadata 完美结合，实现 `BM25 + 向量空间` 的混合搜索 (Hybrid Search)。

## 阶段三：文档结构化解析引擎
- **核心诉求**：解决大模型无法读取二进制办公文档（PDF/DOCX）导致重命名与内容理解退化的问题。
- **决策点 1：PDF 解析方案**
  - **最终选择**：**`pdf-extract` crate**
  - **理由**：在不依赖底层 C 库（如 poppler）的情况下，原生使用 Rust 极其轻量地完成电子 PDF 基本文本与布局抓取。
- **决策点 2：Word (DOCX) 解析方案**
  - **最终选择**：**`zip` crate + 轻量 XML 解析**
  - **理由**：DOCX 本质上是包含 `word/document.xml` 的 ZIP 压缩包。使用原生的 `zip` 库直接读取该文件并剔除 XML 标签，毫秒级提取纯文本。

## 阶段四：「半映射半实际」虚拟数据抽象层
- **核心诉求**：在软件内提供高自由度的 AI 分类与多维重命名，同时 100% 保护 Mac 硬盘实体文件安全，防止第三方程序断链。
- **决策点 1：解耦数据架构**
  - **最终选择**：**虚拟抽象层 (Virtual Name Layer) + 选配物理同步 (Physical Sync)**
  - **理由**：软件内重命名与打标仅修改 SQLite 中的 `virtual_name` 和元数据。预览抽屉清晰显示“虚拟名”与“真实路径”，并提供独立的 `sync_virtual_name_to_disk` 允许用户一键同步物理磁盘。
- **决策点 2：代码工程文件屏蔽策略**
  - **最终选择**：**全量过滤 `.js`, `.py`, `.rs`, `.json`, `node_modules` 等开发工程文件**
  - **理由**：确保检索、智能分类与 AI 命名纯净聚焦于日常办公文档、设计资产与媒体，避免代码文件污染。

## 阶段五：macOS 原生 Apple Vision 本地 OCR 引擎
- **核心诉求**：解决纯图片扫描件 PDF（如试题扫描件 `14.pdf`）以及图像资产无文本数据流导致 AI 命名退回的问题。
- **决策点 1：OCR 引擎选型**
  - **选项**：PaddleOCR / RapidOCR (ONNX) vs 外部云端 OCR API vs Apple Vision Framework
  - **最终选择**：**macOS Native `Vision.framework` (`VNRecognizeTextRequest`)**
  - **理由**：
    1. **零成本 (+0 元)**：100% 本地离线免费运行。
    2. **零包体积 (+0 MB)**：无需打包昂贵的第三方 ONNX 模型，直接调用 Mac 系统能力。
    3. **硬件加速**：在 Apple Silicon NPU 上单页识别耗时低于 100ms，且中文识别率顶尖。

## 阶段六：文件拖拽与收纳盒架构设计 (Dropzone State Mapping)
- **核心诉求**：提供一个临时“收纳区”，允许用户跨视图收集零散文件进行批量处理，并避免破坏真实的物理文件系统。
- **决策点 1：拖拽转移机制**
  - **选项**：方案一（后端虚拟文件夹+原始坐标回滚） vs 方案二（纯前端状态映射）
  - **最终选择**：**方案二（纯前端状态映射）**
  - **理由**：
    1. **解耦后端**：应用“所见非文件而是映射”的核心理念，所有展示的文件均为底层物理文件的内存影子。
    2. **自动隔离**：前端通过 React 的顶层全局状态 (`stagedFiles`) 维持引用的重新分配。拖入收纳盒即过滤掉原列表视图中的显示（`!stagedFiles.includes(file.id)`），实现瞬间消失的转移错觉。
    3. **天然回滚**：当从收纳区移出或清空时，由于全局状态被重置，文件自动复现在原视图，无需设计复杂的坐标回退历史库。
- **决策点 2：拖放安全策略**
  - **最终选择**：**同步内存指针 (`window.__draggedFile`)**
  - **理由**：由于 Tauri 所依赖的 WebKit (Safari) 引擎会在跨越层级边界时由于沙箱策略剥离非标类型的 `dataTransfer` payload（如 application/json），通过 React state 传递加上同步的 Window 内存指针机制，能100%确保安全、不丢数据的高速落入。
