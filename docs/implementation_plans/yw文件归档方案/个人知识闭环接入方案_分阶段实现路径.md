## 一、方案定性：为什么这是「补上缺失的那一半」

### 1.1 两份材料的实质

两个链接不是两个独立能力，而是**同一套方法论的双视角表达**：

|                  | 页面一《个人知识闭环》                                          | 页面二《给产品看》                                                |
| :--------------- | :-------------------------------------------------------------- | :---------------------------------------------------------------- |
| 定位             | 技术方法论 v1.0                                                 | 内部产品评审 Brief                                                |
| 可复用内容       | 三层架构、4 个 HTTP 接口、PARA 五目录、搭建 5 步、Dataview 查询 | 3 大痛点、4 条价值主张、3 类画像、竞品对比、M0–M3 路线、3 个风险 |
| 对本次接入的作用 | **实现蓝图**                                              | **论证框架与叙事**                                          |

**能力内核（唯一）**：

```
Todo 勾选 → 5 字段结构化总结 → 本地桥追加落盘 → Obsidian vault Markdown → Dataview 反向聚合
```

关键指标：单条归档 30 秒 · 写周报耗时降 75% · 产出可追溯率 100%。

### 1.2 与 demo 的能力关系：严格互补，零重叠

| 维度     | 知识闭环                               | 文件管理器 demo                                    |
| :------- | :------------------------------------- | :------------------------------------------------- |
| 数据方向 | **增量生产**——主动创造新记录   | **存量理解**——被动解析已有文件             |
| 语义来源 | 人工填写（产出/卡点/下一步/标签/耗时） | 机器推断（OCR、向量、词库匹配）                    |
| 时间属性 | 天然带时间线（daily note）             | 只有`modified_timestamp` 这类文件系统时间        |
| 核心缺陷 | 只覆盖「我主动记的事」，存量文件盲区   | 只知道「文件里写了什么」，不知道「我用它做了什么」 |

**结论**：demo 现有的 RRF 混合检索能回答"这份文件讲什么"，但回答不了**"我当时用它做了什么、为什么留着它"**。知识闭环补的正是这层**行为语义**。

### 1.3 已验证的三个技术利好

| 利好                    | 证据                                                        | 意义                                                  |
| :---------------------- | :---------------------------------------------------------- | :---------------------------------------------------- |
| `md` 已在白名单       | `lib.rs:18` `is_whitelisted_ext` 含 `"md"`            | vault 设为工作区即可被索引，**零改动**          |
| md 正文可解析           | `file_parser.rs:64` `_ => read_plain_text(p)?` 兜底分支 | daily note 正文自动进`content_snippet` → FTS5 可搜 |
| `.obsidian/` 自动排除 | `lib.rs:413-416` 过滤所有 `.` 开头文件                  | Obsidian 配置目录不会污染索引                         |

**同时存在两个硬约束**：

1. vault **不能放在隐藏目录下**（如 `~/.vault/`），否则整体被 `is_blacklisted_path` 过滤
2. 现有 9 大场景簇词库全是**办公文档语义**（简历/合同/发票/报告…，见 `lib.rs:484-503`），daily note 这类**时间线记录**不匹配任何现有簇，必须新增聚类维度

## 二、核心架构决策：本地桥整层删除

### 2.1 原方案为何需要桥

原方案的工作台是**纯浏览器 HTML**（双击 `index.html` 运行），而浏览器沙箱**无法写本地文件**。因此必须起一个 Node HTTP 服务（`127.0.0.1:7733`）代为落盘。

### 2.2 接入 demo 后这一层是冗余的

demo 是 **Tauri 应用**，Rust 层拥有完整 `fs` 权限，且已在生产使用：

- `move_files_to_staging` —— 真实执行 `fs::rename` / `fs::copy`
- `create_aggregate_folder` —— 真实建目录并迁移文件
- `export_files` —— 真实物理复制

因此三层架构塌缩为两层：

| 原方案                           | 接入后                                                |
| :------------------------------- | :---------------------------------------------------- |
| 工作台 UI（HTML/CSS/Vanilla JS） | →**复用 demo React 前端**                      |
| ~~本地桥 archive-bridge :7733~~ | →**整层删除**，改为 Rust `#[tauri::command]` |
| Obsidian Vault                   | → 保留，作为 demo 的一个工作区                       |

### 2.3 删掉桥消除的全部复杂度

| 原方案需要处理                                | 接入后 |
| :-------------------------------------------- | :----- |
| 装 Node.js 18+                                | 不需要 |
| `./install.sh` 生成 launchd plist、开机自启 | 不需要 |
| 前端 8s 轮询`/health` 判断桥状态            | 不需要 |
| 桥崩溃自拉起（`KeepAlive: true`）           | 不需要 |
| `bridge.error.log` 排障                     | 不需要 |
| 端口被占需同步改`PORT` 与 `BRIDGE_URL`    | 不需要 |

页面一 FAQ 的 6 个问题里有 **4 个是桥的排障**——这些故障类目直接消失。搭建步骤从 5 步降到 2 步（建 vault + 在 demo 设置里指路径）。

### 2.4 接口映射

| 原桥接口                                       | 接入后形态                                         |
| :--------------------------------------------- | :------------------------------------------------- |
| `GET /health`                                | 删除（无桥可查）                                   |
| `POST /archive`                              | `#[tauri::command] archive_file`                 |
| `POST /notes`                                | 暂不做（本期不含随手笔记）                         |
| `GET/POST /config`                           | 合并进 demo 现有`SettingsModal`                  |
| `GET /archives?date=` （原方案的"进阶扩展"） | `#[tauri::command] query_archives`，本期直接内置 |

## 三、归档入口为何落在智能文件夹

### 3.1 现有智能文件夹页面结构（`SmartFolderView.jsx` 526 行）

```
┌─ 顶部状态条：✨ 智能全景聚类 · N 个簇 · M 个资产 · 🔄 重新分类 (295-355 行)
├─ 第二位：AI 动态建簇输入框「输入关键主题词或自然语言」(387-412 行)
├─ 第三位：基础格式速查胶囊 · 图片/文档/表格/媒体 (445-452 行)
└─ 主区：主题簇卡片网格 sortedThemeClusters (505 行)
       └─ SmartFolderCard：📌钉住 / 🗑️解散 / 全视图➔ / 频次沉浮
```

### 3.2 归档能力嵌入的三个位置

| 位置                                    | 新增内容                                                                       | 理由                                                                                     |
| :-------------------------------------- | :----------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------- |
| **A. 新增「知识闭环」分区**       | 独立于「基础格式速查」和「主题簇」之外的第四区，含时间线入口 + 本周聚合卡      | 归档记录的组织逻辑是**时间**，与现有簇的**语义**逻辑不同，混在一起会破坏认知 |
| **B. 簇卡片新增「归档本簇」动作** | 在`SmartFolderCard` 现有三胶囊（📌/🗑️/全视图）后加第四个                   | 天然对应「这一批文件是我为某件事产出的」，簇即天然的归档单元                             |
| **C. 新增 2 个时间线场景簇**      | `smart_scenario_archive`（归档记录）、`smart_scenario_daily`（日记时间线） | 让 daily note 能被现有聚类体系收纳，而非游离在外                                         |

### 3.3 为何不放在文件列表页

文件列表页（`FileListView`）的工具栏已有 `定位 / 导出 / AI 命名` 三个动作，再加「归档」会让工具栏过载；且列表页是**单文件视角**，而归档的心智是**「完成一件事」的批量视角**——智能文件夹的簇天然就是「一件事的产出集合」，语义匹配度更高。

## 四、数据模型设计

### 4.1 Markdown 落盘格式（唯一真源）

沿用原方案格式，确保 Obsidian / Dataview 生态完全兼容：

```markdown
### ✅ 18:14 整理todo+汇总—发给Lancy
- 项目：语音方向 · 优先级：P0 · 耗时：45 min
- 关键产出：14 项 P0 问题列表已整理...
  链接：https://docs.qq.com/doc/xxx
- 卡点：海外语音需求颜色未对齐
- 下一步：明天上午对齐海外需求
- 关联文件：[[语音P0走查清单.xlsx]] · [[海外配色对比.png]]
- 标签：#语音 #P0 #跨团队
```

落盘位置：`{vaultRoot}/30-daily/{YYYY}/{MM}/{YYYY-MM-DD}.md`（文件不存在则建，存在则追加）

> **相比原方案新增 `关联文件` 行**——这是接入 demo 后独有的能力：归档记录与真实文件建立双向链接。

### 4.2 SQLite `archives` 表（派生索引，可随时重建）

```sql
CREATE TABLE IF NOT EXISTS archives (
    id            TEXT PRIMARY KEY,   -- hash(date + time + title)
    date          TEXT NOT NULL,      -- 2026-08-31
    time          TEXT NOT NULL,      -- 18:14
    title         TEXT NOT NULL,
    project       TEXT,
    priority      TEXT,               -- P0/P1/P2
    duration_min  INTEGER,            -- 45（存整数便于求和）
    output        TEXT,
    blocker       TEXT,
    next_action   TEXT,
    tags          TEXT,               -- JSON 数组
    md_path       TEXT NOT NULL,      -- 所属 daily note 绝对路径
    created_at    INTEGER NOT NULL
);

CREATE TABLE IF NOT EXISTS archive_files (
    archive_id    TEXT NOT NULL,
    file_path     TEXT NOT NULL,      -- 关联的真实文件
    PRIMARY KEY (archive_id, file_path)
);

CREATE INDEX IF NOT EXISTS idx_archives_date    ON archives(date);
CREATE INDEX IF NOT EXISTS idx_archives_project ON archives(project);
```

### 4.3 双写一致性策略（关键：把双写降级为「md + 缓存」）

| 规则                                    | 说明                                                                                |
| :-------------------------------------- | :---------------------------------------------------------------------------------- |
| **md 是唯一真源**                 | 任何冲突以 md 正文为准                                                              |
| **archives 表是可丢弃的派生索引** | 表损坏 / 失同步 → 整表 DROP 后从 vault 全量重建，不影响任何真实数据                |
| **用户在 Obsidian 手改 md**       | 下次扫描时按`md_path` + 文件 mtime 检测变更，重新解析该文件所有归档段落并覆盖回填 |
| **不做实时双向监听**              | 不引入 fs watcher，避免复杂度；在「重新智能分类」时统一对账                         |

因此**不存在真正的一致性难题**——代价是需写一个 md 反解析器（约 150 行 Rust）。

### 4.4 双写带来的能力差异（这是选路径 C 的核心理由）

以「整理todo+汇总—发给Lancy / 语音方向 / P0 / 45min」为例：

| 查询需求                 | 路径 A 只写 md               | 路径 C 双写                     |
| :----------------------- | :--------------------------- | :------------------------------ |
| 搜「海外语音」命中该记录 | ✅ FTS5 全文可搜             | ✅                              |
| 显示匹配线索             | ✅ 现有能力                  | ✅                              |
| 列出本周所有 P0          | ❌`P0` 只是正文字符串      | ✅`WHERE priority='P0'`       |
| 语音方向本月累计耗时     | ❌`45 min` 无法求和        | ✅`SUM(duration_min)`         |
| 未闭环卡点清单           | ❌                           | ✅`WHERE blocker IS NOT NULL` |
| demo 内直接出周报素材    | ❌ 需跳 Obsidian 装 Dataview | ✅ 内置聚合                     |

## 七、风险与验收标准

### 7.1 继承自原方案的风险（页面二自陈）

| 风险                        | 原方案表述                                             | 接入 demo 后的变化                                                                                 |
| :-------------------------- | :----------------------------------------------------- | :------------------------------------------------------------------------------------------------- |
| 用户门槛高                  | 需装 Obsidian + Node + 会命令行，天花板 1-2 万人       | **显著缓解**——Node 与命令行不再需要，只剩 Obsidian 依赖                                    |
| 习惯养成坡度陡              | 「勾完 todo 停下花 30 秒填总结」反直觉，3 天后留存未知 | **仍存在**——但归档入口在文件管理器内，用户本来就在此处理文件，触发成本更低                 |
| AI Agent 时代是否还需人手勾 | 核心链路可能 24 个月内被 AI 平推                       | **部分对冲**——demo 已有 Ollama 链路，可逐步把「人手填 5 字段」升级为「AI 预填 + 人工确认」 |

### 7.2 接入引入的新风险

| 风险                                                                      | 应对                                                                                  |
| :------------------------------------------------------------------------ | :------------------------------------------------------------------------------------ |
| vault 放隐藏目录导致整体不被索引                                          | S1 阶段前置校验，`SettingsModal` 选路径时即校验并提示                               |
| 归档功能让智能文件夹页面过载（该页已有状态条+建簇框+格式胶囊+簇网格四层） | S2 严格限制为**一个独立分区**，不散落进现有区块；若视觉过密则改为侧边栏独立入口 |
| 双写失同步                                                                | md 定为真源 + 提供整表重建按钮（S5）                                                  |
| 与现有 9 大簇语义冲突                                                     | 归档簇走**独立分区**，不进 `sortedThemeClusters` 排序池                       |

### 7.3 验收标准
