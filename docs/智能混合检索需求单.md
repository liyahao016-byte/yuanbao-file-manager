
# 【需求单】元宝文件管理器 - 智能混合检索与线索自证引擎

**撰写人**：资深产品经理
**状态**：设计中 / 待评审
**关联模块**：全局搜索、文件列表展现、底层索引引擎

---

## 一、 为什么要做？（核心痛点与业务价值）

### 1.1 背景与痛点：现代文件使用习惯与传统管理机制的断层

在当前的文件管理生态中，用户面临着极大的“找文件难”问题。这并非因为用户懒惰，而是现代文件爆炸式增长，与落后的“树状文件夹/文件名”管理机制之间存在巨大的断层。具体表现为以下四大核心痛点：

1. **不好管（管理结构反人类）**：不论是 Mac 还是 Windows，均采用树状结构储存文件。要求人工分门别类、分层级整理的门槛极高。大多数用户没有时间或能力去维持一个完美的文件夹结构，导致文件堆积如山，成为“文件荒漠”。
2. **容易忘（认知与机器的错位）**：人类大脑的记忆模式是基于“上下文”（如：谁发给我的、干什么用的、里面的某句话），而系统目录只认绝对的文件路径和名称。这种偏移导致用户即使花了大量时间梳理文件夹，过段时间也会彻底忘记文件藏在哪一级目录中。
3. **查不到（盲盒式低效检索）**：
   - 传统搜索严重依赖文件名精确匹配。一旦记不清文件名，就只能人工盲找，极其耗时。
   - 即使支持全文检索的工具（如系统自带资源管理器），不仅速度极慢容易卡死，且结果缺乏“可解释性”。用户看着一堆同名文件，脑海里充满疑问：“为什么搜出这个？”，只能逐个双击打开“开盲盒”，交互成本极高。
4. **怕泄密（隐私安全红线）**：虽然市面上已有部分云端 AI 网盘能帮忙整理和搜索文件，但对于办公资产、个人财务等隐私文件，绝大多数用户极度排斥将数据上云解析。用户强烈呼唤一个“100% 本地化”的安全隐私闭环。

### 1.2 为什么我们的解法最高效？（产品价值论证）

针对上述痛点，我们摒弃了“要求用户去改变习惯”的防守策略，转而采用**“混合检索 + 线索自证 + 纯端侧闭环”**的进攻策略。这是目前解决上述问题最高效、最符合直觉的产品路径：

1. **用“自然语言搜索”打破“不好管与容易忘”的魔咒**
   - **高效性证明**：用户无需再去枯燥地整理文件夹，也不用死记硬背文件名。只要在搜索框输入大脑中残留的“记忆切片”（例如：“上周收到的明年预算表”），系统就能理解这种模糊的业务意图并直接定位目标。这是唯一能完美适配“人类自然认知模式”的检索路径。
2. **用“线索自证（Snippet）”终结“开盲盒式搜索”**
   - **高效性证明**：我们在文件列表中首创了“动态线索展示”。系统不仅给出搜索结果，还能直接在结果下方高亮摘取出正文里匹配的那句话。用户看一眼列表就能确认目标，彻底省去了“双击打开 -> 肉眼寻找 -> 发现不是 -> 关闭寻找下一个”的无效交互，达到了检索效率的理论极限。
3. **用“100% 纯本地架构”守住“绝对隐私”的底线**
   - **高效性证明**：所有的意图理解、内容拆分全部在用户设备的本地闭环完成。断网可用，数据绝不出域。这直接打消了商务人士与企业员工的顾虑，是建立产品信任与高频使用的最强基石。

### 1.3 核心业务目标

做这件事的核心业务目标是：**建立极高的产品壁垒**。
搜索体验是文件管理工具的“命门”，一旦用户习惯了“一搜即得且带自证”的智能体验，对其他竞品的容忍度将直线下降。这能极大提升产品的留存率和 NDS（净推荐值），完成从“冷冰冰的查字典工具”到“懂用户的贴身助理”的范式跃迁。

## 二、 用户需求与场景拆解

### 2.1 典型使用场景 (User Scenarios)

* **场景 A：意图化/语义化检索（忘了文件名，只记得意思）**
  * *用户故事*：小明上个月写了一份关于“下半年新媒体投放预算”的 Excel 报表，但他完全忘了文件名是叫“预算表”还是“投放规划”。
  * *系统表现*：小明搜索“下半年花钱计划”，系统通过向量语义识别，成功召回该 Excel，并在下方展示线索 `✨ 匹配线索：基于 AI 语义与正文检索`。
* **场景 B：碎片化正文检索（只记得里面的一句话或一个号码）**
  * *用户故事*：HR 昨天看了一份简历，只记得候选人的手机号尾数或大学名字“西南财经”。
  * *系统表现*：搜索“西南财经李雅浩”，系统不仅召回文件，还在下方实时展示：`✨ 匹配线索：文件名完全匹配 ｜ 📝 正文包含：“...西南财经大学研究生...”`。用户无需打开文件即可确认这就是他要找的那份简历。
* **场景 C：多维属性检索（模糊的条件组合）**
  * *用户故事*：运营同学想找“上周别人发给我的那些视频”。
  * *系统表现*：系统识别时间意图（上周）、格式意图（视频），并在搜索线索中自证：`✨ 匹配线索：命中时间要求 ｜ 命中格式要求：“video”`。

## 三、 需求详细拆析与产品解法

### 3.1 核心解法：基于 BM25 + sqlite-vec + RRF 的智能混合架构

面对上述“不好管、容易忘、查不到”的问题，如果采用暴力全盘扫描，或者用纯大模型实时读取所有文件（类似无索引的 RAG），在本地端会导致极度卡顿，效率极低。
更高效的核心解法可以拆分分为“底层基建”与“混合检索”两个阶段：

**1. 底层基建：本地私有特征库**
* **离线建库与解析边界**：引入轻量级端语言模型与 Embedding 模型。在后台静默状态下，自动读取用户存储的高价值文件内容。
* **格式全兼容**：除传统的 PDF、Word、Excel、PPT 之外，全面支持解析 `.md` (Markdown)、`.html`、`.txt` 等 AIGC 及开发者常用格式。系统会将这些文件的“文件名 + 正文 + AI摘要”精准提取并转化为高维向量，存入 100% 本地化的 SQLite 数据库（包含倒排索引库与 `sqlite-vec` 向量库）。

**2. 混合检索：四步走智能混合检索流**
* **① 前置解析与 Query 向量化**：当用户在搜索框输入自然语言时，端侧 AI 优先剥离出主题意图、时间、格式诉求（拆成 Json 传给后续节点）；同时，调用 Embedding 模型**将用户的搜索 Query 实时向量化**。
* **② 双通道并行搜**：在本地数据库中双管齐下。通道一：基于 `sqlite-vec` 计算双边向量余弦相似度，提取语义相关的 Top50；通道二：使用 BM25 全文算法进行关键词精准检索，提取字面匹配的 Top50。
* **③ 智能混合重排序 (RRF)**：采用 RRF (Reciprocal Rank Fusion) 混合重排序算法，将多路召回的结果集进行交叉打分。确保精准字面命中的文件排在最前，语义高度相关的紧随其后，输出最终排序。
* **④ 匹配线索策略自证 (Snippet)**：在列表渲染时，系统针对头部结果进行局部嗅探，实时抽取正文中的匹配句并予以高亮展示，向用户给出“为什么搜出它”的直观解释。

### 3.2 方案详述：动态双槽位匹配线索（Snippet）策略

为了让搜索结果“会说话”并消除黑盒感，我们设计了极具解释力的线索展示策略。该策略将底层检索引擎与前端 UI 深度融合，遵循**“应出尽出、聚合截断、极致兜底”**的核心原则。

#### 3.2.1 UI 双槽位展示规范与路由

为避免信息过载，文件列表下方的辅助线索区采用**自适应双槽位（Slot 1 & Slot 2）**矩阵进行渲染。
* **布局与连接**：采用内联区块展示，左侧固定绿色标签 `✨ 匹配线索：`，不同线索间用 `｜` 分隔。
* **数量阈值 (Max-3 原则)**：从 7 个特征维度提取后，必须进行聚合去重。无论单个文件命中多少维度，最终下发至 UI 的线索总数最多不超过 **3 条**。
* **动态路由**：
  * **Slot 1 (主槽位)**：优先承载短文本、高置信度的“实体级”线索（如时间、渠道来源、精准词命中）。
  * **Slot 2 (次槽位)**：主要承载长文本段落、用作补充自证的“片段级”线索（如正文包含的长文摘要）。
* **视觉范例**：
  > 📄 教育部学籍在线验证报告_李雅浩.pdf
  > `[✨ 匹配线索： 来源：浏览器下载 ｜ 📝 正文包含：“...注意事项：1、《学籍在线验证报告》是教育...”]`

#### 3.2.2 线索生成提取优先级矩阵 (后端逻辑层)

当后端混合引擎完成召回和重排序后，将按以下自上而下的严格优先级为每个文件生成线索：

* **[T0] 顶级优先级（高置信特征，对接 Slot 1）**
  * **原文完美匹配**：文件名完整包含用户 Query。 👉 展示：`✨ 文件名完全匹配：“{Query}”`
  * **时间/格式实体命中**：文件的更新时间或扩展名命中前置意图解析。 👉 展示：`✨ 命中时间要求：“上周” ｜ 命中格式：“video”`
  * **渠道/语义主题命中**：路径包含特定系统目录（微信/下载）或符合特定的分类（发票/简历）。 👉 展示：`✨ 来源：微信` 或 `命中语义主题：简历`

* **[T1] 次级片段自证（动态嗅探降级，对接 Slot 2）**
  * 当 T0 层级未能占满 3 条名额时，进入细粒度片段探测（如片段名命中、标签片段命中）。
  * **实时正文嗅探 (核心机制)**：当上述均未命中时。优先从已存入数据库的 AI Suggestion 中寻找片段；若为空（极简补偿），则针对排名前 20 的候选文件，**实时读取本地物理文件的前 1000 个字符进行探测**。一旦触碰到检索词分词，立即截取该词语前后各 15 个字符。 👉 展示：`📝 正文包含：“...{命中词及上下文}... ”`

* **[T2] 终极兜底策略（防误杀与防空白底线）**
  * **触发逻辑**：如果文件纯粹依靠 `sqlite-vec` 的高维语义向量距离被召回（意味着语义绝对相关），但在局部探测时恰好因为文本截断而无法提取出具体的字面匹配片段。
  * **强制兜底**：为了绝对不出现“空荡荡”的黑盒结果，强制赋予兜底提示：`✨ 匹配线索：基于 AI 语义与正文检索`。
  * **闭环控制**：我们放弃了旧版直接将这些文件过滤掉的暴力做法（改走“应出尽出”路线）。如果这些兜底线索的文件真的是垃圾幻觉，系统底层的 RRF 排序引擎会因为它们没有 T0/T1 加分而将其**牢牢压制在列表底部**，从而在保全召回率的同时，绝不污染用户的首屏体验。

## 四、 总结：能够解决什么问题

本需求的落地，从根本上解决了本地文件管理领域长期存在的三大顽疾：

1. **治愈“找不到”**：双引擎召回，让语义相近、正文包含、多维条件的文件无所遁形。
2. **治愈“不敢信”**：线索自证机制（尤其是高亮原文片段），建立人机信任，让用户一眼确信“这就是我要找的”。
3. **治愈“找得累”**：极简的单行 `|` 分割设计配合惰性提炼算法，保证了即使在深层检索下，产品依然保持着轻盈、不卡顿、无冗余视觉负担的旗舰级体验。
