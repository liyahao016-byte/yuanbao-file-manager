# 元宝智能文件管理器 —— AI 命名能力方案

## 1. 背景与目标
在日常文件管理中，用户经常面临文件名杂乱无章、缺乏有效标识（如微信下载的 "wx_camera_1234.jpg" 或未经整理的 "新建文档1.docx"）的问题，导致后期检索和整理成本极高。
**AI 智能重命名**功能旨在结合大语言模型（LLM）的文本理解与实体抽取能力，自动深度解析文件内容特征及上下文语境，为文件生成结构化、规范化且具有高度语义价值的新文件名。

---

## 2. 产品方案设计

### 2.1 交互链路与 UI 呈现
- **入口**：在“全部文件”、“搜索结果”等列表页选中文件后，点击操作栏的「✨ AI 命名」按钮触发。
- **批量预览弹窗 (SmartRenameModal)**：
  - **加载态 (骨架动效)**：在后端大模型分析期间，展示带有“提取内容与元数据中...正在匹配底层分发模板”等专业提示词的动态骨架屏，缓解用户的等待焦虑，并增强 AI 深度计算的感知。
  - **分层对照视图**：结果返回后，以左右对照的形式（`原文件名 ➔ 新文件名`）呈现。
  - **智能类型与模板外显**：针对命名的结果，外显匹配到的逻辑模版特征（如外显标签为 `AI智能提取`，模版为 `{动态实体抽取}`）。
- **确认与应用**：为防止 AI 幻觉，提供“预览 - 确认”两步走机制，用户确认无误后再点击「确认应用模板」执行真实的磁盘重命名。

### 2.2 命名规范与回退原则
- **极简语义化**：遵循 `{内容摘要关键词}-{来源}-{日期}` 的结构。
- **宁缺毋滥**：当某些信息（日期、金额等）无法获取时，强制缺省跳过，绝不允许输出“未知”、“unknown”等字眼。
- **格式保护**：新文件名自动剥离扩展名，确保不会破坏系统文件后缀关联，且摒弃赘余的前缀（如“文档类-”）。

---

## 3. 技术方案设计

本系统采用 `React (前端) + Tauri / Rust (后端) + 本地 Ollama (模型推理)` 的混合架构来实现该功能。

### 3.1 前后端通信设计
前端将用户选中的文件列表提取 `name` 和 `path`，并发调用 Rust 层的 `invoke('rename_with_ai', { path, name })` 指令。

### 3.2 上下文多维度特征构建 (Rust 层)
为了向大模型提供最高效、准确的信息，Rust 侧在发起推理前进行了多维度的特征组装：
1. **内容文本提取 (Snippet Extraction)**：通过 `file_parser::read_text_snippet` 提取文件前 2000 字符的纯文本摘要。
2. **边缘情况兼容 (Scanned/Image PDF)**：如果文件解析后文本为空（如纯扫描件或图片），底层会自动补全特征提示 `[特征：此文件为纯图片/扫描件 PDF，未嵌入矢量文字层]`。
3. **父级目录语境推断**：解析文件的父级文件夹名称。如果是特定的有意义分类名称（如“中微”），则会作为上下文传入；如果是通用系统文件夹（如 Downloads, Desktop 等）则自动忽略，避免干扰模型。

### 3.3 大语言模型推理 (Ollama 层)
- **底层模型**：采用部署在本地端口 (`localhost:11434`) 的 `qwen2.5:32b` 模型进行零样本/少样本提示工程推理，保障本地数据隐私不过云。
- **Prompt 工程 (Prompt Engineering)**：
  - 角色设定：专业的文件整理专家。
  - 指令约束：明确连字符 `-` 或下划线 `_` 拼接规则；禁止输出任何其它冗余字符。
  - 输入特征：注入前面构造好的“所在分类文件夹 + 原文件名 + 内容摘要”。

### 3.4 异常处理与幻觉清洗引擎
针对大模型可能产生的不可控字符（幻觉），Rust 层在获取回复后加入了严格的字符串后处理链路：
1. **幻觉截断**：强行 `.replace()` 过滤掉模型可能生成的 `未知`、`unknown`、`null` 等无意义占位符。
2. **多余前缀清洗**：过滤掉诸如 `其他类-`、`合同类-`、`图片类-` 这样机械呆板的格式化分类前缀。
3. **符号格式化**：处理多余的花括号 `{}`，以及由缺失字段导致的连续标点符号（如将 `--`、`_-` 统一替换为单连接符 `-`）。
4. **终极兜底**：如果经过清洗后的字符串为空，返回 `AI_重命名结果异常` 兜底，防止文件丢失名称。

## 4. 边界场景思考与策略优化 (产品与技术双视角)

### 4.1 针对“乱码文件”与“未命名文件”的边界处理
在实际场景中，用户最痛点的正是微信缓存图片（如 `wx_camera_17823.jpg`）、系统默认命名（如 `新建 Microsoft Word 文档.docx`）、或者纯粹的哈希乱码文件（如 `e5b29f...8a.pdf`）。
- **技术视角的隐患**：当前大模型的 Prompt 会同时注入“原文件名”与“内容摘要”。如果原文件名是乱码，AI 有概率受到干扰，试图在毫无意义的字符中提取信息。
- **优化策略 (已纳入后续迭代)**：
  1. **无意义特征拦截**：在 Rust 侧增加正则判断，若原文件名完全由纯数字、哈希码或“新建文档”等构成，向 AI 发送请求时**直接不提供（或降权）原文件名参数**，强制要求 AI 仅依赖“内容摘要”或“父文件夹上下文”进行从 0 到 1 的推断。
  2. **信息沙漠（零文本 + 乱码名）兜底**：当文件是扫描件/图片（无文本提取），且文件名又是乱码时，AI 将面临“信息沙漠”。此时应采用结构化 fallback 策略：`{父文件夹名称(若有) | 默认类型} + {提取的文件元数据时间}`，例如自动命名为 `微信图片_20260823_1020`，保证起码的可读性。

### 4.2 文件名中的“时间日期”是否冗余？
**用户的思考非常有深度**：既然文件列表视图中已经展示了“操作时间 / 修改时间”，为什么 AI 命名模板 `{内容摘要关键词}-{来源}-{日期}` 中依然保留了日期的空间？

- **视觉上的“伪冗余”**：在元宝文件管理器当前的列表 UI 中，文件名中的日期确实与右侧的操作时间字段产生了视觉重叠。
- **产品视角的“强必要性”（脱离语境后的生命力）**：
  1. **语义时间 vs 系统时间**：系统展示的操作时间往往是“下载时间”或“最后修改时间”（比如今天刚下载了一份去年的报告），而大模型从正文中提取出的日期是**语义时间**（如“2025Q1财务预测”）。这两者完全不同，语义时间才是文件的真实业务节点。
  2. **外带分享属性**：文件不仅仅停留在元宝系统内，一旦用户将文件发送给微信好友、发邮件或拷贝到 U 盘，文件管理器的 UI 字段就**丢失了**。带有业务日期的文件名（如 `李雅浩_个人简历_2026.pdf`）在脱离本系统后，依然能清晰传达信息，避免对方收到一份毫无头绪的 `个人简历.pdf`。
- **优化解法**：在 Prompt 中明确告诫 AI：**仅提取文件正文中代表业务节点的核心时间（如合同签署日、项目周期），绝对不要去拼凑文件的系统创建时间**。若正文无明确时间节点，则缺省不写，依靠列表 UI 字段作为补充。
