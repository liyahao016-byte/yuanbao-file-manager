1

背景与问题分析

1.1 现状描述

当前的"归档时间线"以单条事务为最小单元进行记录，每天完成一件事情就创建一条归档条目，通过标签来暗示这些条目属于同一个需求。数据结构是扁平的：

归档条目 A
标签: #智能搜索
归档条目 B
标签: #智能搜索
归档条目 C
标签: #AI命名
归档条目 D
标签: #AI命名

当前：扁平列表 + 标签隐式关联，缺少需求维度聚合

1.2 核心痛点

痛点 场景描述 频率
老板问进度时无法快速归因 "智能搜索做到哪一步了？" → 需要从几十条归档中人肉筛选带 #智能搜索 标签的条目，再拼凑出进度全景 每周 3-5 次
关键结论散落各处 "上次讨论的 embedding 模型选型结论是什么？" → 聊天记录、文档、飞书消息到处翻 每周 5+ 次
缺少需求全景视图 不知道手头同时推进了几个需求、哪些在进行中、哪些 hold 了、哪些快到 deadline 持续
中间过程无法留存 沟通中的关键截图、方案对比文档、会议纪要没有统一挂载点 每周 3+ 次
下一步 Todo 断链 归档记录的"下一步"与 Todo 系统割裂，需要手动在两个地方维护 每日

1.3 根因分析

根因：缺少"需求"这一层级聚合 当前信息架构只有"日期 → 归档条目"两层，没有"需求 → 节点进展"的父子结构。标签只是弱关联，无法承载需求生命周期管理（状态流转、关键结论沉淀、文档挂载、进度追踪）的职责。
2

产品定位与核心场景

2.1 产品定位

产品需求看板 = 产品经理的个人需求作战室 以"需求"为核心管理单元，记录每一步推进的关键结论、产出、卡点和文档，实现"老板问到哪里，我就能在 3 秒内找到答案"的信息检索效率。

2.2 核心场景

场景 用户故事 验收标准
S1 进度汇报 老板问"XX需求到哪一步了"，我打开看板直接看到该需求卡片：当前阶段、下一步 Todo、卡点 3 秒内找到需求卡片，一屏看全状态
S2 结论溯源 老板问"上次 embedding 选型的结论"，我在搜索框输入关键词，直接定位到某个需求的某个节点记录 搜索结果精确到节点级别，点击跳转到上下文
S3 过程记录 沟通完一个关键结论 / 收到一个重要文档，马上在对应需求下添加一条节点记录，挂载截图或文档链接 30 秒内完成一条节点记录（标题 + 内容 + 附件）
S4 全景管理 周一开工，看一眼看板：4 个需求进行中、1 个 hold、2 个已完成，每个的下一步一目了然 看板视图按状态分列，每列显示需求数 + 摘要
S5 文档聚合 需求涉及的 PRD、评审纪要、设计稿链接、数据报告全部挂在该需求下，不再散落 每个需求有独立的文档/链接挂载区

信息架构重构

3.1 从扁平到树形

旧：归档时间线（扁平）

  • 日期 → 归档条目（平铺）
  • 标签弱关联同一需求
  • 无状态流转概念
  • 无父子关系
  • 搜索只能到条目级别

新：产品需求看板（树形）

  • 需求 → 节点记录（父子结构）
  • 需求有独立状态流转
  • 每个节点是一次关键进展
  • 节点可挂载文档、图片、链接
  • 搜索精确到节点 + 关键词高亮

3.2 新信息架构

每个需求在"进行中"状态下，可标记当前所处的产品工作阶段，帮助精确回答"做到哪一步了"：

评审排期
➔

➔

阶段可自定义 以上为预置的通用产品工作流，用户可根据自身团队流程自由增删阶段。阶段信息直接展示在看板卡片上，一眼可见当前进度。
4

数据模型设计

4.1 新增表：demands（需求表）

CREATE TABLE demands (
  id TEXT PRIMARY KEY, -- UUID
  title TEXT NOT NULL, -- 需求名称，如"智能文件搜索"
  description TEXT, -- 需求简述 / 一句话目标
  status TEXT DEFAULT 'planning', -- planning | active | hold | done
  phase TEXT, -- 当前阶段: 需求调研/方案设计/评审排期/开发联调/测试验收/灰度上线
  priority TEXT DEFAULT 'P1', -- P0 / P1 / P2
  owner TEXT, -- 负责人
  target_date TEXT, -- 期望上线日期
  blocker TEXT, -- 当前卡点
  next_todo TEXT, -- 下一步待办（自动从最新节点同步）
  tags TEXT, -- JSON 数组: ["搜索", "AI"]
  doc_links TEXT, -- JSON 数组: [{name, url, type}]
  sort_order INTEGER DEFAULT 0, -- 看板列内排序权重
  created_at INTEGER, -- Unix 时间戳
  updated_at INTEGER -- Unix 时间戳
);

4.2 改造表：archives → demand_nodes（需求节点表）

改造策略：在现有 archives 表基础上扩展，而非新建 现有 archives 表保留全部字段，新增 demand_id 外键将条目挂载到需求下。未关联需求的旧数据仍可独立显示（兼容旧数据）。
-- 在现有 archives 表上新增以下字段
ALTER TABLE archives ADD COLUMN
  demand_id TEXT REFERENCES demands(id), -- 所属需求 ID（可为空=独立归档）
ALTER TABLE archives ADD COLUMN
  node_type TEXT DEFAULT 'progress', -- progress | conclusion | document | milestone | blocker
ALTER TABLE archives ADD COLUMN
  attachments TEXT, -- JSON: [{name, path, type, url}] 图片/文档/链接
ALTER TABLE archives ADD COLUMN
  is_key_conclusion BOOLEAN DEFAULT 0, -- 标记为关键结论（搜索加权）

-- 创建索引加速按需求查询
CREATE INDEX idx_archives_demand ON archives(demand_id);
CREATE INDEX idx_archives_key ON archives(is_key_conclusion) WHERE is_key_conclusion = 1;

4.3 节点类型说明

node_type 含义 图标 典型内容
progress 进展记录 ▶ "完成了竞品分析文档""前端页面开发完成"
conclusion 关键结论 ★ "选定 bge-m3 作为 embedding 模型""方案 B 评审通过"
document 文档/资料 📄 PRD 链接、评审纪要、设计稿 URL
milestone 里程碑 🏁 "需求评审通过 9/3""灰度上线 9/15"
blocker 卡点/风险 ⚠ "等后端接口 9/5""设计资源排不上"

4.4 新增表：demand_doc_links（需求级文档链接）

CREATE TABLE demand_doc_links (
  id TEXT PRIMARY KEY,
  demand_id TEXT NOT NULL REFERENCES demands(id),
  name TEXT NOT NULL, -- 显示名: "PRD V2.1"
  url TEXT NOT NULL, -- 链接地址
  doc_type TEXT DEFAULT 'link', -- prd | design | meeting | data | link
  created_at INTEGER
);

5.2 看板卡片信息层级

每张卡片需要在有限空间内传达最关键的信息，确保"扫一眼"即可判断状态：

层级 信息 视觉处理
L1 核心 需求名称 14px 加粗，黑色
L2 状态 优先级 + 当前阶段 + 目标日期 12px 灰色，优先级色标 + 阶段标签
L3 风险 卡点信息（如有） 11px 红色/橙色，带警告图标，仅有卡点时显示
L4 下一步 最近一条 Todo 11px 灰色，hover 时显示

5.3 看板交互

快速新建 列底部"+"按钮 弹出精简表单：需求名 + 优先级 + 阶段即可创建
列内排序 拖拽上下 同一列内手动调整优先顺序
筛选 顶部搜索栏 + 标签筛选 保留现有搜索 + 标签筛选能力，改为按需求名 + 节点内容搜索

5.4 视图切换

看板视图为默认主视图，同时保留时间线视图作为辅助
  • 看板视图（默认）：按需求状态四列展示，聚焦全景管理
  • 时间线视图（切换）：保留按日期倒序的节点流水，便于回顾"今天做了什么"
顶部标题栏右侧提供视图切换按钮（看板 / 时间线），切换后记忆用户偏好。

7.2 AI 智能预填增强

AI 预填新增能力
  • 需求智能关联：根据标题 / 语音内容，AI 自动识别应关联到哪个已有需求（基于需求名 + 历史节点语义匹配）
  • 节点类型推断：根据内容语义自动判断节点类型（如含"决定""选定"→ 结论；含"卡住""等待"→ 卡点）
  • 关键结论自动标记：AI 识别高价值结论性内容，自动开启"关键结论"标记

搜索与检索设计

8.1 核心目标

老板问任何关键信息，3 秒内搜到对应节点 搜索范围覆盖：需求名 → 节点标题 → 节点内容 → 附件名 → 标签 → 卡点。搜索结果精确到节点级别，展示"需求名 > 节点标题"的面包屑路径。

8.2 搜索架构

搜索层 索引来源 匹配方式 权重
L1 需求名 demands.title 模糊匹配 最高
L2 关键结论 archives (is_key_conclusion=1) 全文搜索 高
L3 节点标题 archives.title 模糊匹配 中
L4 节点内容 archives.output 全文搜索 中
L5 语义搜索 vec_files (embedding) 向量余弦相似 辅助（当关键词无结果时降级到语义搜索）

8.3 搜索结果展示

搜索结果预览
智能文件搜索 > 关键结论 · 2026-09-01
选定 bge-m3 作为 embedding 模型
对比了 bge-m3 / nomic-embed / mxbai-embed，bge-m3 中文效果最好...
智能文件搜索 > 进展 · 2026-08-28
前端搜索 UI 开发完成，支持关键词 + 语义混合搜索

8.4 搜索交互

  • 输入即搜：防抖 300ms，实时展示结果（保留现有搜索体验）
  • 关键词高亮：搜索关键词在结果中黄色高亮标记
  • 面包屑导航：每条结果展示 "需求名 > 节点类型 > 日期" 路径
  • 点击跳转：点击搜索结果 → 打开对应需求详情面板 → 自动滚动到目标节点
  • 筛选增强：可按需求、节点类型、日期范围、仅关键结论进行筛选

Todo 侧边栏 改造 保留 Todo 追踪能力；Todo 来源从"归档的下一步"改为"需求节点的下一步"，自动关联需求维度

AI 报告生成 改造 改为按需求维度生成周报/月报，聚合各需求的进展节点
右上角呼吸光点 保留 保留现有的待办提醒入口
linkedFiles 附件 增强 扩展为 attachments 字段，支持本地文件 + URL 链接 + 粘贴图片，提供预览缩略图
Markdown 导出 (vault) 改造 改为按需求维度导出：一个需求一个 .md 文件，包含全部节点时间线

9.2 废弃功能

功能 废弃原因
"项目"字段（archive.project） 被"所属需求"(demand_id) 完全替代。旧数据的 project 字段可自动映射为独立需求
标签隐式关联需求 被显式的 demand_id 父子关系替代。标签保留，但职责回归"内容分类"而非"需求关联"

9.3 数据迁移策略

向下兼容：旧数据零丢失
  1. 自动需求生成：遍历旧 archives 的 project 字段，为每个唯一 project 自动创建一条 demand（状态=active）
  2. 自动关联：将同一 project 下的所有 archives 的 demand_id 指向对应的 demand
  3. 无项目的旧条目：demand_id 留空，在时间线视图中照常展示；用户可手动拖入某个需求
  4. 标签迁移：旧数据标签保持不变，仅新数据的标签职责聚焦于内容分类
